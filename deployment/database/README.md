## Roles and trust boundary

| Role | Purpose / privileges |
|---|---|
| `postgres` | Administrator used only by short-lived provisioning jobs |
| `mimir_migrator` | Dedicated database owner, CREATEROLE, can SET ROLE owner; no superuser, CREATEDB, replication or BYPASSRLS |
| `mimir_owner` | NOLOGIN domain-schema/object owner; no superuser or BYPASSRLS |
| `mimir_api` | Non-owner login; schema USAGE on archive/runtime, no DDL or table grants |
| `mimir_worker` | Non-owner login; schema USAGE on archive/runtime, no DDL or table grants |
| `mimir_auth` | Non-owner login; schema USAGE on archive/auth, no DDL or table grants |
| `mimir_maintenance` | Non-owner login; schema USAGE on archive/auth/runtime, no DDL or table grants |

All runtime roles are NOINHERIT, NOCREATEROLE, NOCREATEDB, NOREPLICATION,
NOSUPERUSER and NOBYPASSRLS, with no memberships. TEMP and public schema access
are revoked. Runtime search paths contain only pg_catalog; future application SQL
must qualify domain schema names. Later tasks grant object-specific privileges
and restricted worker/maintenance procedures; no blanket default DML is granted.
Function EXECUTE defaults for owner-created objects are revoked from PUBLIC.

`bootstrap.sql` is administrative cluster provisioning, not a domain migration:
it creates the migrator and dedicated `mimir` database, serializes creation with
an advisory lock, and rejects incompatible existing migration-role/database
ownership. Flyway connects using only the migration secret and applies V001,
which creates the remaining roles and the archive/auth/runtime schemas. A final
provisioning job initializes runtime passwords. New roles cannot authenticate
until their password is set. Passwords are SCRAM verifiers generated by psql's
[password command](https://www.postgresql.org/docs/18/app-psql.html), keeping
plaintext out of SQL, argv, configuration output and logs. Existing passwords
are verified through real logins, never silently rotated or reset on restart.
Keep original credential files with retained data volumes.

The migrator is intentionally privileged: it administers the roles it creates
and can assume object ownership. It must never be used by application/worker
processes. Normal roles cannot assume it or the owner. The backend stays disabled
and receives none of these secrets in T03.

## Explicit operator commands

Prerequisites: Docker daemon access, Compose 5.5.1, uv 0.12.10, Python 3.14.7,
and T02's existing protected bootstrap/Qdrant secrets and external volumes.
Provision the five additional passwords once, from the repository root:

```sh
uv run --project backend --locked python - <<'PY'
import os
from pathlib import Path
import secrets
os.umask(0o077)
directory = Path('deployment/secrets')
for role in ('migrator', 'api', 'worker', 'auth', 'maintenance'):
    with (directory / f'mimir_{role}_password').open('x') as stream:
        stream.write(secrets.token_urlsafe(48))
PY
make database-config
make database-migrate
make database-validate
```

Files must be caller-owned 0600 in a 0700 directory, with no symlink ancestors.
Database passwords must be 32–128 URL-safe ASCII characters (an optional final
newline is accepted), in separate files. This format safely supports psql's
interactive password command over stdin. Alternate protected paths use
`MIMIR_MIGRATOR_PASSWORD_FILE`, `MIMIR_API_PASSWORD_FILE`,
`MIMIR_WORKER_PASSWORD_FILE`, `MIMIR_AUTH_PASSWORD_FILE`, and
`MIMIR_MAINTENANCE_PASSWORD_FILE`. They are file paths, never password values.

`migrate.py` validates the full compiled migration overlay and secret files before
starting PostgreSQL, provisioning the migration login, running Flyway, then
provisioning runtime credentials. Each stage must succeed before the next runs.
Validation/info do not provision or rotate credentials; PostgreSQL must already
be running. The wrapper allows only config/migrate/validate/info. The container
entrypoint rejects clean/repair/baseline/undo, extra flags and injected commands.
No automatic destructive recovery, database major upgrade or volume deletion.

The optional `compose.migrations.yaml` overlay leaves T02's default topology
unchanged. All jobs attach only to the internal private network, publish no ports,
mount reviewed SQL/scripts read-only, and use read-only roots, dropped capabilities
and no-new-privileges. Short-lived jobs run as root with only DAC_OVERRIDE to read
caller-owned 0600 file secrets, following T02's file-mount constraint; no host
privileged mode, socket mount, extra network or backend-secret sharing is allowed.
Writable /tmp is bounded tmpfs. Native macOS Docker runtime remains unverified.

Flyway OSS 12.4.0 is pinned to the multi-platform amd64/arm64 digest in the overlay;
PostgreSQL uses T02's pinned 18.4 image. No Python dependency/lock changes. The
[official Flyway image documentation](https://documentation.red-gate.com/fd/flyway-docker-321585710.html)
describes the OSS image; its digest was resolved with `docker buildx imagetools
inspect flyway/flyway:12.4.0`. Telemetry is disabled and the private network has no
external egress. SQL-only locations are mounted; no Java/Python migrations.

## Validation and recovery evidence

`make backend-check` covers deterministic policy/credential failure paths,
formatting, lint and strict typing. `make database-check` requires a real Docker
engine and fails rather than skips if unavailable. Linux CI runs both, plus the
unchanged T02 container suite; macOS runs deterministic checks only.

The database suite uses unique labelled disposable volumes. It covers fresh V001,
repeat migrate/validate, persistence after container recreation, separate real
role logins, denied DDL/TEMP/escalation/history reads, default grants, forced RLS
with missing/switched transaction-local actors, concurrent Flyway locking,
checksum drift, rejected credentials, and a test-only incremental migration's
transaction rollback/recovery. Test-only RLS tables and synthetic V002 are not
application schema or T04 implementation. Cleanup checks ownership labels and
never touches operator volumes. Exact command outcomes and review SHA belong to
the task PR; test existence is not evidence of a passing execution.

For a failed transactional migration, keep the application closed, inspect the
redacted error/history and confirm rollback; correct only unapplied SQL through
review, then explicitly rerun migrate/validate. A successful V001 has no automatic
down migration. Reverting this task's code does not undo applied SQL or remove
roles/data. Any production rollback needs separately authorized forward SQL or a
coordinated restore under T37; never use repair/clean or delete the retained volume.
If provisioning succeeds but migration/credential verification fails, stop and
resolve the cause; the runner does not expose an application or continue stages.

Full V001–V005 upgrades, production tenant tables/policies, application schema
readiness, user auth and backup/restore remain later-task acceptance. This is not
a release-readiness or native-platform runtime claim.
