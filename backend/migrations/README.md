# Flyway SQL migrations

T03 implements `V001__roles_and_schemas.sql`. T04 implements
`V002__users_identities_and_sessions.sql`. T05 adds
`V003__projects_conversations_and_messages.sql`. T06 adds
`V004__immutable_branch_snapshots.sql`; T07 adds
`V005__runtime_jobs_and_operations.sql` in a separately reviewed PR.
No Alembic or ORM-generated production DDL.
Historical `../appendix/v2-reference/` SQL is non-normative and must not run.

The [database operator guide](../../deployment/database/README.md) documents
provisioning, pinned Flyway, protected role credentials, fresh/repeat/upgrade tests
and failure recovery. The migrator connects as `mimir_migrator`; V001 creates
`mimir_owner` NOLOGIN and four separate, non-owner runtime logins. Domain schemas
are owned by `mimir_owner`. Future migrations must explicitly `SET ROLE
mimir_owner` before creating domain objects and `RESET ROLE` before returning.
Grant only required object privileges with each future table or restricted routine;
T03 intentionally grants no table access or default runtime DML/EXECUTE rights.
Every future user-owned table requires FORCE RLS and real role-session tests.

Flyway history lives in `public`, owned by the migrator and inaccessible to
runtime roles. Only the migration login can assume `mimir_owner`; migration
credentials are privileged administrative material and never runtime credentials.

Never edit/rename an applied migration, use clean, baseline an existing schema,
or repair a checksum without separately authorized operator review. PostgreSQL
transactional migration failure rolls back DDL and history; fix only an unapplied
migration after review, then validate and retry explicitly. Successful migrations
are forward-only. No task here authorizes deleting volumes or restoring production.

## V002 identity and session storage

Authority: [T04 and the owner's implementation clarifications](../milestones/T04_auth-schema.md).
Base `main`: merged T03, `b2a634622781fb474c4d4f0302ede8ff526da5fd`.
The shared contract remains the unchanged draft for S01; T04 adds no HTTP API.

`archive.users` holds stable user IDs, nullable display names and active/disabled
account status. `auth.identities` stores exact case-sensitive unique usernames
(`C` collation) and PHC-encoded Argon2id v19 verifiers. Multiple identities may
reference a user; each identity has immutable ownership. `auth.sessions` is keyed
by the 32-byte SHA-256 token hash, with a composite owner/identity FK and explicit
client type, issue time, last use, idle/absolute expiry and revocation timestamps.
There is no plaintext bearer or refresh token column. IDs are supplied by trusted
application code (UUIDv7), not generated by this migration.

Expiry and activity timestamps must be finite and ordered. The absolute ceiling,
session credential hash, owner/identity, issue time and client type are immutable.
Revocation cannot be cleared or changed. Activity/idle expiration cannot move
backwards, and an expired or revoked session cannot be renewed. At the absolute
ceiling equality is allowed for idle expiration, never for last use. T08 owns
the 30-day idle/90-day absolute issuance policy, password/PHC verification and
resource limits; SQL checks validate storage shape and lifecycle invariants,
not cryptographic validity or successful authentication.

All three tables have ENABLE/FORCE RLS. Tenant policies use transaction-local
`app.current_user_id`; missing context sees no tenant rows and malformed context
fails closed. Only `mimir_api`/`mimir_worker` receive tenant-scoped user SELECT;
API may update only `display_name`. No runtime role receives direct identity or
session table access, provisioning, account-status writes or purge privileges.
T08 must supply its separately reviewed restricted provisioning/session mutation
interfaces; T04 does not implement those services or grant broad maintenance DML.

`mimir_auth` can execute only these pre-authentication lookup functions:

| Routine | Input | Result for one match |
|---|---|---|
| `auth.lookup_identity(text)` | Exact username | User/identity IDs, password verifier, account status |
| `auth.lookup_session(bytea)` | SHA-256 credential hash | User/identity IDs, client type, last use, expirations, revocation, account status |

Unknown/null inputs and incorrectly sized session hashes return zero rows.
Disabled/revoked/expired matches expose their state to the internal auth service;
they are not an authenticated principal. T08 must validate credentials and state
before setting actor context in each application transaction. No lookup sets
actor context, creates an account, renews a session or returns a bearer secret.

These static SECURITY DEFINER functions run as the existing NOLOGIN owner,
with fixed `pg_catalog, pg_temp` search path, schema-qualified references and
`row_security=on`. Explicit SELECT-only policies for that owner allow lookup
before tenant context exists even under FORCE RLS. The caller inherits neither
table access nor owner membership; PUBLIC/other runtime logins cannot execute
the lookups. Owner writes still require tenant context. V001's existing privileged
migrator can assume the owner; it must never be an application credential.

`make database-check` runs T03 against V001 and T04 against real V001/V002,
including fresh/repeat/restart, real logins/RLS, negative integrity/lifecycle
cases, concurrency, actual V002 upgrade rollback/recovery and checksum drift.
The tests use uniquely labelled disposable databases, not operator volumes.
The [T04 test evidence mapping](../../TRACEABILITY.md) describes partial coverage;
actual command results and the submitted SHA are recorded in the T04 PR.

If V002 fails, PostgreSQL transactional DDL must roll back tables, functions and
Flyway history. Keep services closed, confirm rollback, review/correct only
unapplied SQL, then explicitly migrate/validate again. After successful V002,
reverting Git does not undo the schema. Any reversal requires separately approved
forward SQL or a coordinated restore; never edit applied V001/V002, clean/repair
history or remove retained volumes. Account purge/restore remains T35/T37 work.

## V003 archive storage

Authority: the owner's explicit T05 lifecycle/immutability clarification in
[FINAL_V1](../../docs/decisions/FINAL_V1.md) and the
[T05 brief](../milestones/T05_archive-core-schema.md). Initial base was merged T04,
`105d4747299ab317c0d5dda5469d892bcdbc66e2`; submission base is
`e9a122836f09ff9256aa20d346c2b422f9982363`, including merged deployment correction
PR #6. V001/V002 are unchanged.

V003 adds owner-scoped projects (optional instructions), nullable-project
conversations, canonical messages and separate immutable content revisions.
Conversations begin at version 1. Metadata changes require an increasing version;
versions and update timestamps cannot move backwards. Application CAS and
message/run/version atomicity remain T10/T12/T16 work. No automatic message-insert
version increment substitutes for those transactions.

Messages have only `completed` status. To insert a message/revision pair, first
insert the message with either its intended revision ID or a null pointer; insert
its revision; fill the pointer if initially null; commit. The same-owner,
same-message FK is deferred and the deferred trigger rejects a null final pointer.
The selected pointer cannot be changed once non-null, even before commit. This
deliberately stronger insertion rule removes any need to detect transaction age.
Committed message identity, owner, conversation, ordinal, role/status and creation
time cannot change; all revision updates are rejected. Revisions may be appended
with dense numbers but can never replace an already selected revision or edit
canonical history. The normal v1 creation path selects its initial revision.

Local message ordinals and per-message revision numbers start at 1 and append
densely under parent-row locks in READ COMMITTED. Consecutive user messages are
allowed. Revisions store exact `text/v1` content (at most 1 MiB UTF-8 bytes) and an
insertion-derived SHA-256 digest. No extension or application dependency is added.
Branch inherited ordinals/snapshots are T06 work; no branch schema is supplied.

All four tables ENABLE/FORCE RLS, use composite owner FKs and belong to the
NOLOGIN owner. API/worker can read their tenant's archive and insert message pairs;
API can create/update project/conversation metadata; worker can advance conversation
version/update time. Messages expose only pointer UPDATE for insertion ordering.
Auth/maintenance have no archive table grants. No runtime receives DELETE,
TRUNCATE, revision UPDATE, DDL or direct trigger-routine EXECUTE. Restricted purge
interfaces remain T35/T36 work, not a global immutability bypass switch.

The deferred completeness trigger runs as owner with a fixed search path and
`row_security=on`. A SELECT-only owner policy on messages lets it inspect its exact
owner/message even after transaction actor context is cleared/switched. Other
logins gain neither owner membership nor direct routine access; no SECURITY DEFINER
write interface or broad runtime policy is introduced.

`make database-check` includes real fresh V001–V003, V002-to-V003 upgrade, migration
rollback/retry, repeat/validate/restart, drift, runtime RLS/grants, immutable history,
commit guard, UTF-8 boundaries, dense numbering and competing append/CAS tests.
Tests use labelled disposable volumes; production/operator volumes are untouched.
Schema and data rollback are exercised, not simulated by an ORM.

If unapplied V003 fails, keep service closed, verify transactional rollback and
unchanged V001/V002 history, review/correct only unapplied SQL, then explicitly
migrate/validate. After success, Git revert does not undo schema: reversal requires
separately approved forward SQL or coordinated restore. Never edit applied
migrations, repair/clean history or delete retained volumes.

Cross-domain runtime transactions, inference, managed-memory delivery, branch
snapshots, checkpoint retention and explicit failed-attempt retries are not
implemented or verified by V003. Shared `Message.status` contract reconciliation to
`completed` only still needs separate authorization; no contract artifact changes.

## V004 immutable branch snapshots

Authority: [T06](../milestones/T06_branch-schema.md),
[FINAL_V1](../../docs/decisions/FINAL_V1.md) and the approved branch modes in
the shared contract. Base `main` is merged T05,
`f12d4c78921aa5cacba3229b2846ac408a0b2f15` (PR #7). V001–V003 are unchanged.

Conversations gain immutable parent, exact branch-point revision, branch mode
and derived inherited-prefix length. Roots retain null linkage and zero inherited
length. A new branch must supply its parent's current project association;
association changes after creation remain independent. The parent row is locked
before reading its history, sharing V003's READ COMMITTED append/metadata lock.
The point must be an exact selected revision in that parent's visible history.
`after_revision` includes the point; `replace_message` excludes it, allowing an
empty prefix when replacing the first message. Neither mode starts inference.

In one transaction, insert the branch conversation, then insert its complete
ordered prefix into `archive.conversation_branch_revisions` before commit.
Each entry stores only owner, child conversation, visible ordinal, message ID and
exact revision ID. Composite FKs enforce owner/message/revision relationships.
An immediate invoker-rights insertion guard rejects ordinals above the frozen
prefix length using one owned-conversation lookup, without scanning snapshots.
Positive ordinals and uniqueness remain table constraints. One deferred check per
new conversation counts its final references and compares them with the exact
parent prefix using a set difference. Missing, reordered, gapped or substituted
references cannot commit, even when trusted code has cleared/switched actor
context. The complete validator is not queued per reference. Parent linkage and
prefix length cannot change; snapshot UPDATE is rejected, including by the owner.
A complete prefix occupies every slot from one through its frozen length, so
uniqueness plus the immediate upper bound also forbid later extension, including
after an explicit successful `SET CONSTRAINTS ALL IMMEDIATE`.

`archive.conversation_visible_revisions` is a security-invoker view combining
flattened inherited references with local messages. V003's local ordinals still
start at one; visible local ordinals add the frozen prefix length. Nested branches
copy references from this view, never text. Parent appends, appended unselected
revisions, or project reassignment cannot rewrite inherited history; canonical
content/pointer mutation remains prohibited by V003.

The new table ENABLEs/FORCEs RLS. API can insert tenant snapshots; API/worker can
read the table/view. No runtime snapshot UPDATE/DELETE/TRUNCATE, direct trigger
EXECUTE, owner membership or worker branch INSERT is granted. The deferred
SECURITY DEFINER trigger has a fixed search path and `row_security=on`;
SELECT-only owner policies on conversations/snapshots support actor-independent
commit validation. No runtime definer write interface is added. FKs retain
dependent parents/revisions until a separately authorized subtree purge.

`make database-check` includes `test_t06_*` real PostgreSQL 18/Flyway fresh,
repeat, restart, V003 upgrade, transactional DDL rollback/retry and checksum drift
tests, plus nested branches, boundary/negative cases, role/RLS checks and competing
branch/append/delete transactions. Tests use labelled disposable volumes only.
Large-prefix tests cover 1,000/2,000/5,000 references from root and nested parents,
assert one full-validator invocation per new conversation with transaction-local
PostgreSQL function counters, and report transaction timings through successful
commit. Function tracking is configured only in the isolated test stack; runtime
permissions and deployment configuration are unchanged. Multiple insertion
statements/branches, early constraint checks and extension of empty/complete
snapshots are regression cases. Timing reports are measurements, not release SLOs.
The [traceability mapping](../../TRACEABILITY.md) describes partial storage
acceptance; actual command results and submitted SHA belong to the PR.

For failed unapplied V004: keep services closed, verify V003 history/data remain
intact and V004 objects rolled back, review/correct only unapplied SQL, explicitly
retry migrate, then validate. After successful V004 there is no down migration:
Git revert does not undo schema. Reversal requires separately approved forward
SQL or coordinated offline restore. Never edit applied history, repair/clean
checksums, or remove retained volumes.

PR #8 review R1 corrects the candidate V004 validation mechanism within T06.
The owner confirmed V004 had only been applied to disposable test databases and
authorized this correction; no retained migration history is rewritten. Existing
disposable databases with the old checksum must not be repaired for reuse.
Recreate only owned disposable test stacks from the revised candidate. Applied
non-disposable V004 would instead require separately authorized forward SQL.

No branch service/HTTP producer, version/idempotency transaction, inference,
memory ingestion or governed subtree purge is implemented here (T10/T11/T12,
T16/T33 and T35/T36 retain those boundaries). No contract/dependency changes;
S01 validation and the recorded `Message.status` reconciliation remain pending.

## V005 runtime storage

T07 is based on merged T06 main `a562761ebd8dc5804b78e39e073bee5a7999c918`.
V001–V004 remain unchanged. V005 adds eight owner-scoped operational tables:

- `model_runs`: conversation/standalone shape, owned input/output message roles,
  one active conversation run, executor token/generation/lease, monotonic
  checkpoints, cancellation request, terminal state and standalone expiry.
- `model_run_attempts`: per-run attempt identity, one open attempt, provider/token
  metadata, nonnegative usage and immutable terminal/visible-output evidence.
- `jobs`: claim/retry/reconciliation states, bounded attempt counter, token and
  generation, lease/heartbeat shape, claim/FIFO/expired-lease indexes and one
  running memory-ingestion job per user. Independent users remain concurrent.
- `memory_ingestions`: delivery metadata for an exact successful conversational
  user/assistant revision pair, original project hint and provider configuration;
  deduplication follows the approved pair/configuration identity. This is not
  provider-owned managed-memory content or a canonical memory table.
- `operation_ledger`: owner/type/key uniqueness, 32-byte request fingerprint,
  typed run/conversation/message/version identities, accepted/terminal status,
  30-day retained identity, following 30-day tombstone window and separate
  resolution evidence. Identity/fingerprint/retention boundaries are immutable.
- `outbox_events`: optional durable publication records, with an unpublished
  index. This schema does not mandate a duplicate job-publication hop.
- `context_assembly_records`: selected source IDs, token budgets, policy versions
  and degradation/truncation diagnostics; no assembled prompt or memory text.
- `deletion_controls`: restricted account-purge control metadata and established
  journal/fence identity, with approved lifecycle states. PostgreSQL metadata is
  **not** the independently durable restoration journal; T35/T37 must implement
  that journal, verified fencing/purge and replay before service exposure.

Every table has ENABLE + FORCE RLS and composite owner foreign keys for live
relational references. Operation response IDs are historical evidence: the
acceptance trigger verifies their owned source rows and makes identities
immutable, without FKs that would prevent retention after source deletion. A
retained response ID never grants access to the original resource. API and
worker privileges are explicit; neither gets DDL, DELETE,
TRUNCATE, owner membership or routine EXECUTE. API cannot claim/finalize runs or
jobs. Auth/maintenance have no direct runtime table access. No runtime role gets
direct writes to deletion controls. Restricted cross-user discovery, purge and
cleanup interfaces belong to later tasks, not an RLS bypass in V005.

Standalone input is temporary `input_text`, limited to 1 MiB UTF-8 and permitted
only on standalone runs. It is protected by forced tenant RLS and explicit table
privileges; API/worker roles cannot rewrite it. Per approved architecture section
10, encryption at rest is provided by encrypted host volumes and backups, without
application field-level encryption or application-managed input keys. This
schema/test suite does not provision or verify host/backup encryption. Prompts
must remain absent from logs, diagnostics and operation lookup responses.
T21/T23 own bounded input retention and cleanup services; no new input TTL is
selected here. Completed standalone results expire exactly 168 hours after
completion. Expired result/input/checkpoint erasure can preserve run
and ledger identity through an artifact-purge marker; only privileged schema
tests can exercise that shape today. No runtime cleanup privilege or worker is
installed. Unsuccessful checkpoint retention and explicit inference retry remain
unresolved by the approved T05 clarification; V005 invents no TTL/replay policy
for them. T21/T23 own retention services. Unresolved operation evidence has no
cleanup eligibility until resolution, even after the tombstone boundary.

Lease columns and state guards are storage prerequisites, not an implementation
of the T16/T32 executor/queue protocol. Trusted services must use expected state,
token/generation and lease validity predicates in their UPDATE statements.
Tests exercise competing SQL claims, stale-token no-ops, terminal races and
expiry/reconciliation; they do not establish safety of a future service. Lease
duration (2m), heartbeat cadence (30s), FIFO selection and retry backoff (5s capped
at 5m) remain T32 behavior. No automatic inference replay or Mem0 call occurs.
T12/T16/T33 retain atomic submission/finalization/enqueue and ingestion services.

`make database-check` includes fresh/repeat/restart V001–V005, V004-to-V005
upgrade with a retained branch archive, deliberately failed migration
rollback/recovery, checksum drift, actual runtime roles, RLS on/off/missing scope,
constraints, negative/boundary cases and competing PostgreSQL transactions.
The tests use only unique labelled disposable stacks. See the T07 PR for actual
commands/results and reviewed SHA; no public API/E2E acceptance is implied.

If unapplied V005 fails: keep serving closed, confirm V001–V004 history and data
are unchanged and runtime objects/grants/functions rolled back; review/correct
only the unapplied candidate, explicitly rerun migrate, then validate. After a
successful V005, a Git revert is not a database rollback. Use separately approved
forward SQL or a coordinated offline restore of compatible archive/provider
stores with independent deletion-journal replay before reopening (T37). Never
edit applied SQL, run Flyway clean/repair/baseline/out-of-order migration, or
delete retained volumes. V005 installs no down migration or destructive recovery.
