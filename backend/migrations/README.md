# Flyway SQL migrations

T03 implements `V001__roles_and_schemas.sql`. T04 implements
`V002__users_identities_and_sessions.sql`. T05–T07 own V003 archive, V004 branches
and V005 runtime/jobs, each in a separately reviewed PR.
No Alembic or ORM-generated production DDL.
Historical `../appendix/v2-reference/` SQL is non-normative and must not run.

The [database operator guide](../../deployment/database/README.md) documents
provisioning, pinned Flyway, protected role credentials, fresh/repeat/upgrade tests
and failure recovery. The migrator connects as `mimir_migrator`; V001 creates
`mimir_owner` NOLOGIN and four separate, non-owner runtime logins. Domain schemas
are owned by `mimir_owner`. Future migrations must explicitly `SET ROLE
mimir_owner` before creating domain objects and `RESET ROLE` before returning.
Grant only required object privileges with each future table or restricted routine;
T03 intentionally grants no table access or default runtime DML/EXECUTE rights.
Every future user-owned table requires FORCE RLS and real role-session tests.

Flyway history lives in `public`, owned by the migrator and inaccessible to
runtime roles. Only the migration login can assume `mimir_owner`; migration
credentials are privileged administrative material and never runtime credentials.

Never edit/rename an applied migration, use clean, baseline an existing schema,
or repair a checksum without separately authorized operator review. PostgreSQL
transactional migration failure rolls back DDL and history; fix only an unapplied
migration after review, then validate and retry explicitly. Successful migrations
are forward-only. No task here authorizes deleting volumes or restoring production.

## V002 identity and session storage

Authority: [T04 and the owner's implementation clarifications](../milestones/T04_auth-schema.md).
Base `main`: merged T03, `b2a634622781fb474c4d4f0302ede8ff526da5fd`.
The shared contract remains the unchanged draft for S01; T04 adds no HTTP API.

`archive.users` holds stable user IDs, nullable display names and active/disabled
account status. `auth.identities` stores exact case-sensitive unique usernames
(`C` collation) and PHC-encoded Argon2id v19 verifiers. Multiple identities may
reference a user; each identity has immutable ownership. `auth.sessions` is keyed
by the 32-byte SHA-256 token hash, with a composite owner/identity FK and explicit
client type, issue time, last use, idle/absolute expiry and revocation timestamps.
There is no plaintext bearer or refresh token column. IDs are supplied by trusted
application code (UUIDv7), not generated by this migration.

Expiry and activity timestamps must be finite and ordered. The absolute ceiling,
session credential hash, owner/identity, issue time and client type are immutable.
Revocation cannot be cleared or changed. Activity/idle expiration cannot move
backwards, and an expired or revoked session cannot be renewed. At the absolute
ceiling equality is allowed for idle expiration, never for last use. T08 owns
the 30-day idle/90-day absolute issuance policy, password/PHC verification and
resource limits; SQL checks validate storage shape and lifecycle invariants,
not cryptographic validity or successful authentication.

All three tables have ENABLE/FORCE RLS. Tenant policies use transaction-local
`app.current_user_id`; missing context sees no tenant rows and malformed context
fails closed. Only `mimir_api`/`mimir_worker` receive tenant-scoped user SELECT;
API may update only `display_name`. No runtime role receives direct identity or
session table access, provisioning, account-status writes or purge privileges.
T08 must supply its separately reviewed restricted provisioning/session mutation
interfaces; T04 does not implement those services or grant broad maintenance DML.

`mimir_auth` can execute only these pre-authentication lookup functions:

| Routine | Input | Result for one match |
|---|---|---|
| `auth.lookup_identity(text)` | Exact username | User/identity IDs, password verifier, account status |
| `auth.lookup_session(bytea)` | SHA-256 credential hash | User/identity IDs, client type, last use, expirations, revocation, account status |

Unknown/null inputs and incorrectly sized session hashes return zero rows.
Disabled/revoked/expired matches expose their state to the internal auth service;
they are not an authenticated principal. T08 must validate credentials and state
before setting actor context in each application transaction. No lookup sets
actor context, creates an account, renews a session or returns a bearer secret.

These static SECURITY DEFINER functions run as the existing NOLOGIN owner,
with fixed `pg_catalog, pg_temp` search path, schema-qualified references and
`row_security=on`. Explicit SELECT-only policies for that owner allow lookup
before tenant context exists even under FORCE RLS. The caller inherits neither
table access nor owner membership; PUBLIC/other runtime logins cannot execute
the lookups. Owner writes still require tenant context. V001's existing privileged
migrator can assume the owner; it must never be an application credential.

`make database-check` runs T03 against V001 and T04 against real V001/V002,
including fresh/repeat/restart, real logins/RLS, negative integrity/lifecycle
cases, concurrency, actual V002 upgrade rollback/recovery and checksum drift.
The tests use uniquely labelled disposable databases, not operator volumes.
The [T04 test evidence mapping](../../TRACEABILITY.md) describes partial coverage;
actual command results and the submitted SHA are recorded in the T04 PR.

If V002 fails, PostgreSQL transactional DDL must roll back tables, functions and
Flyway history. Keep services closed, confirm rollback, review/correct only
unapplied SQL, then explicitly migrate/validate again. After successful V002,
reverting Git does not undo the schema. Any reversal requires separately approved
forward SQL or a coordinated restore; never edit applied V001/V002, clean/repair
history or remove retained volumes. Account purge/restore remains T35/T37 work.
